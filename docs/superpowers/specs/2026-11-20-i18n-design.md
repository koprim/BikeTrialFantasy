# Internationalisation (fr, es, en) — Design Spec

> État : validé (brainstorming 2026-11-20). Branche `feat/i18n`.

## Objectif

1. Le jeu s'affiche en **français, espagnol ou anglais** : interface **et** textes de jeu (cartes, effets, saisons, manches).
2. La langue est **détectée** automatiquement et **modifiable** par le joueur.
3. **Ajouter une langue** = un dossier de textes + une ligne dans un registre. Aucun code, aucune migration.
4. Une page **Infos** dit que le jeu est en développement et montre la part traduite de chaque langue.

Hors périmètre : mails d'authentification Supabase, noms propres (pilotes, lieux, arbitres sur les manches), messages de validation du catalogue (outil de développement, restent en français), langue enregistrée dans le profil (plus tard, avec le profil avancé).

## Choix techniques

- `i18next` + `react-i18next` (traduction, pluriels, interpolation `{{value}}`), `expo-localization` (langue de l'appareil ou du navigateur).
- Le choix du joueur est enregistré sur l'appareil (AsyncStorage, clé `language`).
- Les adresses web (`/collection`, `/regles`…) ne changent pas selon la langue.

## 1. Registre des langues

`src/i18n/languages.js` est le **seul** endroit qui déclare les langues :

```js
export const LANGUAGES = [
  { code: 'fr', name: 'Français', ui: require('./locales/fr/ui.json'), game: require('./locales/fr/game.json') },
  { code: 'en', name: 'English',  ui: require('./locales/en/ui.json'), game: require('./locales/en/game.json') },
  { code: 'es', name: 'Español',  ui: require('./locales/es/ui.json'), game: require('./locales/es/game.json') },
];
export const REFERENCE_LANGUAGE = 'fr'; // langue complète, base du pourcentage
export const FALLBACK_LANGUAGE = 'en';  // affichée quand une clé manque
```

Le sélecteur, la détection, l'initialisation d'i18next, la page Infos, le rapport de traduction et le script de seed lisent ce registre. Aucun autre fichier ne cite un code de langue.

`require` statiques : Metro (web et mobile) ne sait pas charger un dossier dynamiquement ; la ligne du registre est donc la seule étape manuelle.

## 2. Textes : un dossier par langue

```
src/i18n/
  index.js            initialise i18next depuis le registre
  languages.js        registre
  detect.js           choix de la langue de départ
  progress.js         pourcentage traduit par langue
  game.js             gameText(): textes de jeu localisés
  locales/
    fr/ui.json        interface (référence)
    fr/game.json      textes de jeu (référence)
    en/…  es/…
```

### ui.json

Clés regroupées par écran : `tabs.*`, `season.*`, `compose.*`, `collection.*`, `cardDetail.*`, `standings.*`, `history.*`, `rules.*`, `account.*`, `infos.*`, `errors.<ApiErrorCode>`, `team.<code>`, `rarity.C|R|E|L`, `eventStatus.*`.

### game.json

Textes de jeu rangés par identifiant :

```json
{
  "cards": {
    "technique-2026-gap": { "name": "Gap", "effects": ["+{{value}} pts s'il réussit un Gap"] }
  },
  "seasons": { "2025": { "name": "Coupe du Monde 2025" } },
  "events":  { "2025-r1": { "name": "Coupe du Monde 2025 — Manche 1" } }
}
```

Les 63 cartes y figurent toutes, y compris les cartes pilote et arbitre dont le nom est un nom propre : les brouillons `en` et `es` recopient ces noms tels quels.

### Données mécaniques

`src/data/seed/cards.json` et `seasons.json` ne gardent que la mécanique : identifiants, types, raretés, déclencheurs, récompenses, dates, lieux, résultats. Les champs `name` (cartes, saisons, manches) et `effects[].description` sont retirés et partent dans `locales/fr/game.json`. `riders.json` ne change pas (noms propres).

Les générateurs (`scripts/gen-dev-seed.js`, `scripts/build-seed.js` via `src/data/seedBuilder.js`) écrivent la mécanique dans `src/data/seed/*.json` et les textes français dans `locales/fr/game.json`. Les autres langues sont écrites à la main et ne sont jamais écrasées.

`src/engine/catalog.js` ne vérifie plus `name` / `description` dans les données mécaniques. Un test vérifie que chaque carte, saison et manche a son texte dans `fr/game.json`.

### Accès aux textes de jeu

`gameText(lang)` dans `src/i18n/game.js` renvoie des fonctions `cardName(id)`, `effectText(cardId, index, value)`, `seasonName(id)`, `eventName(id)`. Chaîne de repli : langue choisie → `FALLBACK_LANGUAGE` → `REFERENCE_LANGUAGE`. Le formatage de la valeur (`formatValue` de `effects.js`) reste dans le moteur ; seul le gabarit de phrase vient de la langue. Les écrans l'utilisent via un hook `useGameText()`.

### Supabase

Une migration convertit une fois pour toutes en `jsonb` de la forme `{ "<code>": texte }` :

- `seasons.name`, `competitions.name`, `cards.name` ;
- `effects[].description` dans `cards.effects`.

`scripts/build-sql-seed.js` (qui écrit `supabase/seed.sql`) assemble ces objets à partir de tous les dossiers de langue du registre. Ajouter une langue ajoute une clé : pas de nouvelle migration. Le serveur ne lit pas ces textes (il ne calcule que la mécanique).

## 3. Le moteur renvoie des codes

- `validateCardTeam` renvoie `errors: [{ code, slot }]`, par exemple `{ code: 'RIDER_ALREADY_IN_TEAM', slot: 'eliteWomen2' }`, au lieu de phrases. Un code par message existant.
- Le serveur transmet ces objets tels quels dans les détails de `INVALID_TEAM` ; l'écran les traduit (`team.<code>`, avec le libellé du poste traduit).
- Les libellés des postes (`SLOTS[].label`) sortent du moteur : clés `compose.slots.<slotId>`.
- `RARITY_LABELS` sort de `rarity.js` ; le moteur ne connaît que `C/R/E/L`, l'interface affiche `rarity.<code>`.
- `src/ui/eventLabel.js` et `src/ui/errorMessages.js` passent par `t()`.

## 4. Langue et page Infos

### Langue de départ (`detect.js`)

1. Choix enregistré dans AsyncStorage, s'il est déclaré dans le registre ;
2. sinon, première langue de l'appareil (`getLocales()`) présente dans le registre (`es-MX` → `es`) ;
3. sinon `FALLBACK_LANGUAGE`.

L'application attend ce choix avant le premier affichage (même mécanisme que le chargement de la partie), pour éviter un écran qui change de langue.

### Sélecteur

Une section « Langue » dans Règles liste les langues du registre par leur nom (« Español »). Le changement s'applique immédiatement et est enregistré.

### Page Infos (`/regles/infos`)

Accessible depuis Règles (un lien ; elle passera dans le pied de page avec le futur habillage de site). Elle affiche :

- le jeu est en développement et mis à jour régulièrement ;
- pour chaque langue du registre : nom, pourcentage traduit, barre de progression.

Pourcentage (`progress.js`) = clés présentes et non vides dans `ui.json` + `game.json` de la langue, divisé par le nombre de clés du français. Calculé à partir des fichiers, rien à mettre à jour à la main. Le français affiche 100 %.

## 5. Tests et outillage

- Unitaires : chaîne de repli de `gameText`, `detect.js` (choix enregistré, langue d'appareil avec région, langue inconnue), `progress.js`, nouveaux codes de `validateCardTeam`.
- Cohérence, pour chaque langue du registre : ses fichiers existent, toutes ses clés existent en français, les variables `{{…}}` sont les mêmes que dans le texte français.
- Les tests d'écran existants restent en français : l'environnement de test démarre en `fr`.
- Un test d'écran : changer de langue dans Règles fait passer les onglets en anglais.
- `npm run i18n:report` liste, par langue, les clés manquantes et le pourcentage.

## 6. Contenu

- `fr` : textes actuels, déplacés sans changement.
- `en` et `es` : brouillons complets écrits pendant l'implémentation, à relire par un locuteur natif. La page Infos affichera donc 100 % pour les trois langues tant qu'aucune nouvelle clé n'est ajoutée sans traduction.

## Ajouter une langue (exemple : allemand)

1. Copier `src/i18n/locales/fr/` vers `src/i18n/locales/de/` et traduire, même partiellement.
2. Ajouter la ligne `de` dans `src/i18n/languages.js`.
3. `npm run i18n:report` pour voir ce qui manque ; `npm run build:sql-seed` pour régénérer `supabase/seed.sql`.
